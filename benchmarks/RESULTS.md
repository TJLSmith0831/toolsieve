# Routing benchmark results

On a catalog of 181 tools from 25 real MCP servers, toolsieve puts the right tool in front of the client **85% of the time on 3 tools instead of 181** — **98.3% fewer tokens** than loading the catalog into context.

On queries that share no vocabulary with the tool's own description — the `paraphrase` tier, and the case lexical search is worst at — it finds the tool **70%** of the time against BM25's **32%**.

Generated by `benchmarks/run_benchmark.py`. Re-run it after any material change to the catalog or the router — these numbers are quoted in the README.

## Setup

- **Catalog**: 181 tools across 25 real MCP servers (`catalog.json`)
- **Queries**: 159 with ground-truth expected tools, tagged exact / paraphrase / ambiguous (`queries.jsonl`)
- **Tokenizer**: `tiktoken/cl100k_base` — a real tokenizer, not toolsieve's runtime chars/4 estimate
- **Embedding model**: `BAAI/bge-small-en-v1.5` (toolsieve's shipped default)
- **k**: 3 for the ranked methods. Recall is scored at the number of tools each method actually delivered, so naive — which dumps the whole catalog unranked — is scored against all of it rather than against a top-3 it never claimed to produce.

`saved` is measured against loading the whole catalog of that size into the client's context, which is what an MCP client does with no sieve in front of it. The `tokens` column is the total across every scored query at that size, not a per-call figure — compare rows within a catalog size, and read `saved` for the headline, since it is independent of how many queries were scored.
